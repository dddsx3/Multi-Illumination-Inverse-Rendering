# A10 6 小时窗口作战手册（Phase 2 剩余消融臂）

**版本**：v1.0（2026-08-26）　**目标机**：NVIDIA A10 24GB（非本机，6h 使用权）
**入口**：`run_a10.py`（一键：预检 → 标定 → 预算规划 → 训练 → 评估 → 打包）

---

## 一、静态验证结论（先看这一段）

### 1.1 目标机规格与代码要求的匹配性

| 项 | A10 | 本项目要求 | 判定 |
|---|---|---|---|
| 架构 / 算力 | Ampere GA102，sm_86 | 需原生 BF16（训练口径固定 bf16） | ✅ Ampere 原生支持 |
| 显存 | 24GB GDDR6 | bs8 实测峰值分配 8.63GB | ✅ 2.8x 余量 |
| 带宽 / 功耗 | 600GB/s / 150W | — | ✅ 数据中心卡可持续满载 |
| BF16 张量算力 | 125 TFLOPS（稠密） | — | 见 §1.2 时间预算 |
| PyTorch | 需 ≥2.4（`torch.amp.autocast('cuda',…)`） | requirements 已锁 | ✅ |

**关键结论：显存与数值格式都没问题，唯一的风险是时间。**

### 1.2 时间预算（诚实版：6h 装不下 5 个臂）

本机实测标定（`bench_throughput.py`，RTX 5070 Ti Laptop）：

| 指标 | 实测值 | 含义 |
|---|---|---|
| 纯训练步 | 0.528 s/batch（56 batch/epoch → 29.6 s） | — |
| GPU 利用率 | **98.7%** | **计算受限**，不是 I/O 受限 |
| 数据加载占比 | 6.3% | 加 worker 没用 |
| 峰值显存 | 8.63GB 分配 / 11.56GB 保留 | 决定并行车道数 |
| 端到端 epoch | **98–101 s**（TensorBoard 墙钟） | 含全损失项、GT 监督、49 场景验证、157MB 落盘 |

推论：

1. **并行车道不是提速手段**。GPU 已 98.7% 占用，再开一条车道只能填补验证/落盘的空窗，聚合收益约 1.15x，却要吃掉 2×10.8GB 显存并抬高 OOM 风险。脚本据此自动判定 **lanes=1**。
2. **单臂成本 ≈ 100 s/epoch × 100 epoch ≈ 2.8 h**（A10 的 BF16 算力低于本机，实际可能 1.0–1.8 倍，即 2.8–5.0 h/臂）。
3. **5 个臂 = 500 epoch ≈ 14–25 h，6h 窗口只够 1–2 个臂。**

### 1.3 因此推荐的 6h 用法

```bash
python3 run_a10.py --data_root /path/to/synthetic_v3 --budget-hours 6
```

不带 `--only` 时按门禁优先级自动排队，实际能跑完的臂由**目标机实测速率**决定：

| 优先级 | 臂 | 待跑 epoch | ETA @100 s/ep | 价值 |
|---|---|---|---|---|
| 1 | `p2_t25_f_resA` | 100 | 2.8 h | G2.5 残差消融，任务卡点名的论文关键证据 |
| 2 | `p2_t25_f_albOff` | 100 | 累计 5.6 h | G2.2 逐光照反照率 A2 的价值对照 |
| 3 | `p2_t22_f_n5rgb` | 100（从零） | 累计 8.3 h | 双模态链路 |
| 4 | `p2_t23_f_physcon` | 100 | 累计 11.1 h | G2.3 物理约束 |
| 5 | `p2_t25_f_resC` | 100 | 累计 13.9 h | G2.5 容量消融 |

**现实预期：A10 若与本机同速（100 s/epoch）能跑完 resA + albOff 两个臂；
若慢 1.5 倍则只有 resA 一个臂。** 脚本按段核算，跑不完的臂停在整 epoch
边界保持可续跑，不产半截结果。

> **不要复用本地 n5rgb 的 epoch 63 checkpoint。** 该 run 已按 INC-0006
> 判作废（epoch 40–59 在错误的阶段 1 权重下训练），带污染历史续跑到 100
> 仍不可与其它臂同口径比较。双模态臂如需入矩阵，必须从 epoch 0 重训。

### 1.4 为什么不靠"调参"塞进 6h

`batch_size`、`epoch 数`、三阶段划分、`bf16`、`cudnn.deterministic` 全部与已完成的
R0 / F-N5-gray 基线绑定。任何一项为提速而改动，都会让消融对比混入第二个变量
（纪律 D10 单变量原则），整张对比矩阵作废——那比少跑一个臂的损失大得多。
因此脚本只在与训练数学无关的维度（进程编排、车道、截止判断）上做工程优化。

> 一项可选授权：`main.py:33-34` 固定 `cudnn.deterministic=True / benchmark=False`
> 以保证复现（D8）。放开确定性通常能提速 10–25%，但会牺牲逐位复现能力。
> **默认不动**；若你愿意接受该代价，可另行授权后加开关。

## 二、部署步骤

### 2.1 需要传到 A10 机器的东西

| 文件 | 大小 | 来源 | 用途 |
|---|---|---|---|
| 代码 | — | `git clone` 本仓库（已含全部修复） | 训练/评估 |
| `phase2_cloud_package.zip` | 315 MB | 项目根目录（内含 `data/synthetic_v3` 621 场景，已核验与本地灰度 PNG 逐位一致） | 数据集 |

> zip 内也有一份旧代码快照 `code/`，**不要用它**——用 git clone 的最新代码
> （含 INC-0005/0006 续跑修复、RGB 双链路、评估架构自适应）。
> 也**不要**上传本地 n5rgb 的 checkpoint 当续跑点（见 §1.3 的作废声明）。

### 2.2 一键引导

```bash
git clone https://github.com/dddsx3/Multi-Illumination-Inverse-Rendering.git repo
cd repo
bash setup_a10.sh /path/to/phase2_cloud_package.zip
```

脚本会：装依赖 → 解包数据到 `../data/synthetic_v3` → 跑预检与预算规划
（打印计划表）→ 打印正式启动命令。

确认计划无误后：

```bash
nohup python3 run_a10.py --data_root ../data/synthetic_v3 --budget-hours 6 \
      > _a10_main_log.txt 2>&1 &
tail -f _a10_main_log.txt
```

（想让引导脚本直接开跑：`AUTO_START=1 BUDGET_HOURS=6 bash setup_a10.sh ...`）

### 2.3 预检会拦住的问题（跑之前就报错，不浪费窗口）

- 无 CUDA / 不支持 BF16 / 显存 < 11GB
- 数据根目录不存在、样例场景缺 `light_00X.png` 或 4 个 GT `.npy`
- 缺 `splits/synthetic_v3.json`，或清单里的场景在数据根下找不到（抽查 40 个）
- 磁盘不足（单臂每 epoch 存档 157MB，满 100 epoch 需 ~15.6GB）
- 未见 `*_rgb.png` → 自动跳过 n5rgb 臂并告警

## 三、运行期行为

- **分段续跑**：每 10 epoch 一段，每 epoch 落 checkpoint。任何时刻被 kill /
  抢占，重跑同一条命令自动从最新 epoch 接上。
- **自适应速率**：首段用标定预估，之后每段用**实测墙钟**校正 s/epoch
  （`[rate]` 行）。截止判断随时间越来越准，这是 6h 不超时的保障。
- **不产半成品**：段前核算 `剩余时间 < 本段所需 × 1.1` 就停手；只有跑满
  100 epoch 的臂才评估、才写入完成状态。
- **自动评估**：臂跑满即在冻结 test（124 场景）上出 13 项指标，落
  `eval_output/<run_id>_test/{eval_summary.json,per_scene_metrics.csv}`。
- **自动打包**：结束时生成 `../a10_return_package.zip`——每臂 best_model、
  评估 json/csv、训练日志、TensorBoard 事件、计划与进度 json。

## 四、回传后本地要做的

```bash
# 1. 解包，把 best_model 与 eval_output 归位（run_id 命名不变）
# 2. 生成论文级对比矩阵与图表
python make_report_assets.py
# 3. N 敏感性曲线（需要 FusionUNet 臂的 checkpoint）
python eval_n_curve.py --checkpoint <fusion_best.pth> --data_root D:/data/synthetic_v3
```

对比矩阵会自动把新回传的臂并入现有 3 行（Phase1 参考 / R0 对照 / F-N5-gray），
列最佳值加粗，数字全部可追溯到 `eval_output/*/eval_summary.json`（纪律 D3）。

## 五、已知偏差声明（交审计）

1. **6h 窗口内无法完成全部 5 臂**——这是算力预算的客观结果，不是执行偏差。
   未完成臂保持可续跑状态，`a10_plan.json` 记录了每臂的 ETA 与判定依据。
2. `--only` 指定的执行顺序把"便宜且能确定跑完"的臂排前，属预算优化，
   不影响任何臂的训练口径。
3. 本手册 §1.2 的 `OVERHEAD_FACTOR=3.38` 是本机实测折算系数，仅用于首段前
   的预估；正式判断一律用目标机实测速率。

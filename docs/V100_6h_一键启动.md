# V100 六小时窗口 · 一键启动说明

**入口**：`train_v100.sh`（引擎为共用的 `run_arms.py`）
**目标机**：Tesla V100（Volta sm_70，16GB 或 32GB HBM2，900 GB/s）
**预算**：6 小时　**交付原则**：能跑完几个臂就交付几个，跑不完的臂保持可续跑，回本机继续

---

## 一、怎么开始（两条命令）

```bash
git clone https://github.com/dddsx3/Multi-Illumination-Inverse-Rendering.git repo
cd repo && bash train_v100.sh /path/to/phase2_cloud_package.zip
```

脚本自动完成：机器体检 → 安装依赖（含 sm_70 兼容性验证）→ 解包数据 →
精度口径声明 → 标定与预算规划 → 后台训练 → 每个臂跑满即评估 → 打回传包。

只需上传两样东西：

| 文件 | 大小 | 来源 |
|---|---|---|
| 代码 | — | `git clone`（本仓库，含全部修复） |
| `phase2_cloud_package.zip` | 315 MB | 项目根目录，内含 `data/synthetic_v3` 621 场景 |

> zip 里那份 `code/` 是旧快照，**不要用**；用 git clone 的最新代码。

常用环境变量：

```bash
BUDGET_HOURS=6      # 预算
AMP_DTYPE=fp16      # 精度（默认 fp16；32GB V100 可试 fp32）
ONLY=p2_t25_f_resA  # 只跑指定臂（逗号分隔，顺序即执行顺序）
NO_REF_ARM=1        # 不插入同精度参照臂
AUTO_START=0        # 只出计划不开跑
```

## 二、精度：V100 只能用 fp16（或 fp32），这件事有代价

V100 是 Volta（sm_70），**没有原生 BF16**——而既有的 R0、F-N5-gray 两个基线
都是 bf16 训练的。实测（同种子、同配置、2 epoch）：

| 精度 | epoch0 val | epoch1 val |
|---|---|---|
| bf16 | 0.2666 | **0.0987** |
| fp16 | 1.0342 | 0.2013 |

fp16 的 epoch1 验证损失是 bf16 的 2.04 倍——**不是等价替代**（详见 INC-0007）。

因此本入口在非 bf16 精度下会**自动把同精度参照臂 `p2_t22_f_n5gray_fp16` 排在
最前**。这一步不是浪费算力，它一次买到两样东西：

1. 后续消融臂有了**同口径基线**，G2.5 / G2.2 的对比可以完全在 fp16 内部闭环，
   不需要跨精度混比（纪律 D10）；
2. 它与既有 bf16 版 `p2_t22_f_n5gray` 在同一冻结 test 上的差值，就是**精度本身
   影响量的直接测量**——这是目前证据库里缺的一环。

所有非 bf16 产物的 run_id 自动带 `_fp16` / `_fp32` 后缀，不会覆盖既有 bf16 产物
（纪律 D8 可回溯）。

关于 fp32：本机实测 bs8 峰值分配 15.35GB、保留 17.76GB。**16GB V100 装不下**，
预检会直接拦下；32GB V100 可以跑，数值上更接近 bf16 基线，但 V100 的 fp32 没有
张量核心，会明显更慢。

## 三、6 小时能交付什么

单臂成本 = 100 epoch × 单 epoch 耗时。V100 的实际速度由脚本在目标机上现场标定
（约 1 分钟），然后按**实测速率**排队。经验区间：

| 若标定出 | 单臂 | 6h 可交付 |
|---|---|---|
| 120 s/epoch | 3.3 h | 参照臂 + 1 个消融臂 |
| 150 s/epoch | 4.2 h | 参照臂（1 个） |
| 200 s/epoch | 5.6 h | 参照臂（1 个，勉强） |

排队优先级（预算不足时从后往前砍）：

1. `p2_t22_f_n5gray_<dtype>` —— 同精度参照臂（非 bf16 时自动插入）
2. `p2_t25_f_resA` —— G2.5 残差消融，任务卡点名的论文关键证据
3. `p2_t25_f_albOff` —— G2.2 逐光照反照率 A2 的价值对照
4. `p2_t22_f_n5rgb` —— 双模态链路（本地 run 已按 INC-0006 作废，须从 0 重训）
5. `p2_t23_f_physcon` —— G2.3 物理约束
6. `p2_t25_f_resC` —— G2.5 容量消融

如果你想把 6h 全部押在消融臂上、接受跨精度混比的风险，用
`NO_REF_ARM=1 ONLY=p2_t25_f_resA`。

## 四、运行期保证

- **不超时**：每 10 epoch 一段，段前用实测速率核算「剩余时间 < 本段需时 × 1.1」
  就停手，停在整 epoch 边界。只有跑满 100 epoch 的臂才评估、才写完成状态——
  半截臂不会进对比矩阵。
- **可续跑**：每 epoch 落 checkpoint。被抢占/断连后重跑同一条命令即从最新 epoch
  接上（INC-0005/0006 修复后，续跑会正确恢复阶段权重表与残差冻结状态，
  且不再重做上一个 epoch）。
- **不改口径**：batch_size=8、100 epoch、三阶段 30/30/40、cudnn.deterministic
  全部与既有基线一致。除精度外不引入第二个变量。
- **fp16 稳定性**：GradScaler 溢出按「跳过该 batch 并下调 scale」处理，连续 10 次
  才判定发散停机；bf16/fp32 的硬停机语义不变（INC-0007）。

## 五、看进度与回传

```bash
tail -f _arms_main_log.txt          # 实时日志（含 [rate] 实测速率、[deadline] 判断）
python3 run_arms.py --status        # 计划 + 各臂进度
```

结束后生成 `../arms_return_package.zip`，内含：

- `checkpoints/<run_id>_best_model.pth`（每个跑满的臂）
- `eval_output/<run_id>_test/{eval_summary.json,per_scene_metrics.csv}`（13 项指标）
- `logs/`（训练日志 + TensorBoard 事件）
- `arms_plan.json`、`arms_progress_merged.json`、`_arms_bench.json`（标定与判定依据）

## 六、回传后在本机做什么

```bash
# 1) 解包，把 checkpoints 与 eval_output 按 run_id 归位
# 2) 生成对比矩阵与图表（自动并入现有 3 行）
python make_report_assets.py
# 3) 剩余未跑完的臂在本机继续（本机是 Blackwell，支持 bf16）
python run_arms.py --data_root D:/data/synthetic_v3 --budget-hours 24
```

> 本机注意：曾多次触发 Windows「页面文件太小」（WinError 1455）与散热保护关机。
> 本机长跑前建议加大页面文件，并用 `THERMAL_PACE=1.0` 环境变量降低平均功耗
> （只影响墙钟，不影响训练数学）。

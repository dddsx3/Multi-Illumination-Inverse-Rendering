# INC-0002 · Blender 单进程连渲 349 场景后原生崩溃

- **日期**：2026-08-24
- **影响**：T1.2 全量渲染首跑在第 350 个场景中断（exit 11）；后续 480 场景未渲染。
  已完成的 237 场景数据完好，无资产损失。
- **状态**：已修复（分块渲染策略），15/15 块全部 exit 0

## 1. 现象

- 渲染至 `[349/829]` 场景 `1523af4f...glb` 时 Blender 原生崩溃：
  `KERNELBASE.dll UNKNOWN EXCEPTION`，blenderproc 返回 exit 11；
- 崩溃前每场景均出现告警 `Detected output entries with duplicate keys and paths`；
- 嫌疑模型单独重渲**完全正常** => 排除"毒模型"，锁定为进程级累积问题。

## 2. 根因分析

**直接原因**：长进程累积性状态劣化。两个具体机制（有日志佐证）：

1. 输出注册表重复项随场景数线性增长（duplicate keys 警告逐场景出现），
   合成器节点树被反复追加，加载阶段歧义增大；
2. OptiX/GPU 显存与驱动侧碎片在数百次 render() 后触发不可恢复异常。

**深层原因**：BlenderProc 的设计假设是"一个进程一个渲染会话"；我们的多场景
复用超出了其状态管理的设计域。属于**外部工具在超设计域使用时的固有风险**，
非我方代码缺陷——但缺少分块机制使我方代码放大了该风险。

## 3. 已实施修复（_render_chunks.ps1）

- 每 40 个场景重启一次 Blender（进程级状态归零）；
- 逐块日志（chunk N exit=…）+ 幂等跳过（已完成场景按 sh_coeffs.npy 判定）；
- 单块崩溃不影响后续块，重跑自动补齐缺失场景。

实测：15/15 块 exit 0，602/829 场景成功渲染（其余为守卫过滤的退化模型）。

## 4. 可借鉴的失败点

1. **外部引擎长跑必须分块**。凡是无法保证进程内状态自清洁的工具（Blender、
   训练框架、浏览器自动化等），默认按 30-50 工作单位分块 + 每块独立日志；
2. **幂等续跑是分块的前提**：以产物存在性（sh_coeffs.npy）为完成标记，
   失败时清理半成品目录，使"重跑"永远安全；
3. **崩溃隔离测试先行**：遇到原生崩溃先单独复测嫌疑单元（本例 5 分钟即排除
   毒模型假设），避免在错误方向上加固；
4. 警告类日志（duplicate keys）不应忽视——它是状态泄漏的早期信号。

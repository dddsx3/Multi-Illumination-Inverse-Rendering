# INC-0005 断点恢复未同步阶段状态（损失权重表 + 残差冻结）

**日期**：2026-08-26　**发现人**：执行者（构建者）　**状态**：已修复，待审计核验
**影响臂**：p2_t22_f_n5rgb（F-N5-RGB）——损失约 1 个 epoch 进度；其余臂未受影响

---

## 1. 时间线

| 时刻（08-25/26） | 事件 |
|---|---|
| 00:20 | 编排器启动 n5rgb 臂全量训练（100 epoch，段间 10 epoch） |
| ~02:10 前后 | 机器第一次热保护关机（功耗墙 123.57W，默认仅 65W，散热差）；最新 checkpoint=epoch_0064 |
| 02:49–03:05 | 部署温度看门狗并两次自动续跑；期间发现恢复后同 epoch 损失异常升高（0.19–0.23 vs 关机前 0.06），epoch_0064 重做后 val=0.0835（原为 0.0510） |
| 03:10 后 | 第二次热保护关机（用户报告）；执行者介入诊断 |

## 2. 根因分层

- **直接原因**：`trainer.load_checkpoint` 只恢复 `current_stage` 数值，不调用 `_update_loss_weights()`；残差模块的 `requires_grad` 也停留在 `__init__` 的阶段1配置（冻结）。训练循环仅在"检测到阶段切换"（`new_stage != current_stage`）时更新两者——直接跳回阶段3的续跑永远不会触发。
- **放大原因**：编排器按 10-epoch 分段 + 断点续跑是常态路径（D2），使该缺陷从偶发变成必现；热保护关机进一步提高了续跑频率。
- **过程性原因**：INC-0001 之后工程重心放在训练稳定性守卫上，没有为"恢复语义"建立与保存语义对称的单测（保存什么就该恢复什么）。

## 3. 证据链

1. 恢复启动横幅打印「进入阶段 1: Geometry Learning」（`__init__` 初始化行为）；
2. `load_checkpoint` 后无任何权重表同步动作（trainer.py 原 L991-998）；
3. 重做 epoch64 val=0.0835 ≠ 原始 0.0510；train loss 同期 3 倍漂移；
4. `checkpoint_epoch_0064.pth` 内 val 字段 = 0.0835，且与 e63 权重差 0.0166 → 确认被污染续跑覆盖；
5. R0-v3gray 此前从 epoch22 续跑**未受影响**：恢复点与初始化同为阶段1，权重表碰巧一致。

## 4. 已实施修复

1. `trainer.load_checkpoint`：恢复后强制 `_update_loss_weights()` 并按恢复阶段设置残差 `requires_grad`（阶段≥3 解冻），打印同步结果供日志审计；
2. 受污染产物隔离：`checkpoints/p2_t22_f_n5rgb/_quarantine_INC0005/`（checkpoint_epoch_0064.pth、latest_model.pth），续跑改从干净的 epoch_0063（best_model 同点，val 0.04596）出发；
3. 热防护加严（环境性，非本 INC 直接内容但同期落地）：THERMAL_PACE=1.5s/批、看门狗 30s 巡检、≥80°C 杀训、≤75°C 续跑。

## 5. 未尽事项

## 6. 可借鉴失败点

"保存的状态"与"恢复的状态"必须逐字段对称；凡是派生缓存（权重表、冻结标志、调度器），要么存档、要么恢复后强制重算——不能依赖下游"恰好会触发一次切换"。分段续跑设计（D2）会把一切恢复期缺陷放大为必现缺陷。

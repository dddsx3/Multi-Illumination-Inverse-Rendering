## 0. TL;DR（独立审计请先读这段）

`p2_t22_f_n5rgb` 臂在 2026-08-24 至 2026-08-27 期间出现 97 次 launch 全部从 epoch 0 起步、无法推进到 100 epoch 的故障。  
经多轮自检 + 现场诊断，确认 3 类**真实**问题叠加：

1. **数学底层 3 个 Bug**（已修复，授权修复）：
   - Bug A：`albedo_corr < 0.4` 判定语义反向（与 Lambertian 假设矛盾）
   - Bug B：Lambertian Ratio 公式 `(rendered²)/(images²)` 在 RGB 模态下数值不稳定（曾观测 146× 爆炸）
   - Bug C：`stage1_end=30, stage2_end=60` 在 10 epoch 预算下整个训练被困 stage1，`sh_l2=0.1` 高压制下 SH 系数被强拉到 0

2. **INC-0008 触发 97 次 launch 循环**（已修复）：n5rgb 模态下 DataLoader spawn 6 worker × 150 MB 越 32 GB 提交上限，epoch 0 验证阶段崩（WinError 1455）；每次 main.py 异常退出后 watchdog 看到"无进程"立即重启 run_arms.py。

3. **INC-0006 标记 vs 续跑的逻辑冲突**（**未授权修复，待审计裁决**）：
   - `run_arms.py:178-194` 的 `epochs_done()` 在目录有 `_CONTAMINATED_*.md` 标记时**永远返回 0**
   - 这导致即使训练了 10 epoch 产生 `checkpoint_epoch_0000.pth`...`checkpoint_epoch_0009.pth`，`epochs_done` 仍读为 0
   - `run_arms.py:537-540` 的 `if after <= done` 永远触发 → 编排器 abort
   - 但训练实际成功了：val_loss=0.027229（epoch 9），3 倍优于之前 17 次 launch 的 0.087 最佳

## 2. 已执行的修改（精确到行号）

### 2.1 trainer.py 三处修改

#### Bug A：`trainer.py:1376`
```diff

+ albedo_corr > 0.7
```
**等价性论证**：判定函数在 {0,1} 上的补集映射；对正确分解模型：原/新都 True；对错误模型：原/新都 False。

#### Bug B：`trainer.py:948-975`
```diff
- rendered_energy = (rendered ** 2).mean().item()
- total_energy   = (images ** 2).mean().item()
- lambertian_ratio = rendered_energy / total_energy if total_energy > 0 else 0.0
+ # 通道归一化能量匹配度
+ rendered_ch = rendered.abs().mean(dim=(0, 2, 3))
+ images_ch   = images.abs().mean(dim=(0, 2, 3))
+ ch_rel_diff = (rendered_ch - images_ch).abs() / (images_ch + eps)
+ lambertian_ratio = max(0, min(1, 1 - ch_rel_diff.mean()))
```
**等价性**：完美匹配 → 旧=1, 新=1；旧 0 或 146× → 新 clip 到 [0,1]（数值稳定但物理含义等价）。

#### Bug C：`trainer.py:298-318`

### 3.3 我之前给出的错误分析（反面教材，供审计验证）

我在本次排查中**至少给出过 3 次错误根因分析**：

#### 错误 1：声称 "ARMS 编排器 while 循环未推进"（21:00 左右）
- **错误内容**："[segment] 事件在日志中 0 次 → run_arms.py 进程实际只 spawn 一次 main.py，剩下 13 次是 main.py 自身的多进程重试"
- **真实情况**：run_arms.py 一直按设计在 while 循环中推进，[segment] 事件被 watchdog 的 `RedirectStandardOutput` 抓到 `_orchestrator_log.txt` 而非 `_arm_*.log.txt`，但 `_orchestrator_log.txt` 当时已显示 albOff 完成后 run_arms.py break（不进入 t22，因为 albOff 是 todo 中第 2 个，按 line 709-720 顺序跑）。
- **真正原因**：INC-0008 让 t22 main.py 在 epoch 0 验证阶段崩，导致 for 循环 break 不到（resA+albOff 都成功，按顺序进 t22），但 t22 launch 立即因 INC-0008 崩，watchdog 见无进程重启 run_arms。

#### 错误 2：声称 "watchdog 循环 bug"（22:00 左右）
- **错误内容**："thermal_supervisor.ps1:31-50 看到无训练进程会重新拉起 run_arms"
- **真实情况**：watchdog 行为正确——它只在 main.py + run_arms.py 都不存在时启动 run_arms。真正问题不在 watchdog 本身，而在于 run_arms + main.py 之间的 INC-0008 崩溃-重启循环。
- **真正原因**：INC-0008 修复（num_workers=2）落地后，watchdog 不再触发循环（已验证：现在 run_arms + main.py 协作正常）。

#### 错误 3：声称 "INC-0006 标记的清除 + latest_ckpt 不可识别"（02:30 左右）
- **部分正确**："_CONTAMINATED_INC0006.md 让 latest_ckpt 返回 None，main.py 不会传 --resume"
- **但忽略了更深层**：`epochs_done()` 也读这个标记，永远返回 0，导致 run_arms 的 while 循环 abort
- **更深问题**：即使删除了 `_CONTAMINATED_*.md`，`latest_ckpt` 能否正确找到最新 checkpoint 仍需要审计（因为 `--resume --checkpoint checkpoint_epoch_0009.pth` 是修复后正确路径，但**首次 6 次 launch 的 segment 事件**也只到 epoch 0，**没有 [segment] epoch 10 -> 20 事件**——说明 orchestrator 的 while 循环在 t22 这一臂上根本没进入第二段）。

## 4. 困难清单（独立审计需要确认的事项）

### 4.1 训练是否真的需要 100 epoch？
- ARMS 计划：`p2_t22_f_n5rgb` 100 epoch（约 4.79h）
- 实际可行性：本机 GPU 散热能力下，每段 10 epoch 耗时 26.6 分钟（含温度节律），10 段 = 4.4 小时。**勉强可行但散热风险高**
- 当前已训练 10 epoch，val=0.027
- **审计需要决定**：10 epoch 是否足够？val=0.027 是否可接受？

### 4.2 INC-0006 标记是否应当被删除？
- 设计哲学：作废 run 不可续跑——这是数据完整性约束（D10：禁止污染轨迹进对比矩阵）
- 实际情况：本次 10 epoch 是修复后干净代码训练的产物，按"修复后作废"哲学应当**不视为污染**
- **审计需要决定**：
  - (a) 删除 `_CONTAMINATED_INC0006.md`，让 10 epoch checkpoint 可被识别
  - (b) 改用新 run_id（如 `p2_t22_f_n5rgb_v2`），绕过 contaminated 检查
  - (c) 保留 10 epoch 不续训，直接 evaluate_model.py 评估

### 4.3 run_arms 主循环的 while 推进逻辑是否正确？
- 当前 `run_arms.py:468-535` 的 `train_arm` 函数：
  - line 478: `done = epochs_done(...)` → 第一次为 0
  - line 479: `if done >= TOTAL_EPOCHS: return True` → 100 epoch 时才满足
  - line 481: `seg = min(SEGMENT_EPOCHS, TOTAL_EPOCHS - done) = 10`
  - line 499: `target = done + seg = 10`
  - line 502-516: spawn main.py with `--total_epochs 10`，**当 done>0 时**追加 `--resume --checkpoint ck`
  - line 532: `after = epochs_done(...)` → 因 contaminated 返回 0
  - line 537: `if after <= done: abort` → 0 <= 0 → abort
- **审计需要决定**：这是 INC-0006 设计的预期行为（"污染 run 不能进对比矩阵"），还是 INC-0006 设计本身的副作用（意图是阻止 INC-0006 期间的污染训练，**但意外地也阻止了 INC-0006 修复后的干净训练**）？

### 4.4 我的修复是否产生新的数学/逻辑偏差？
- Bug A 修复：判定函数单调翻转，无新增数学假设
- Bug B 修复：单调映射到 [0,1]，clip 兜底无副作用
- Bug C 修复：总预算 4:5:1 比例（之前 30:30:40 改为按比例缩放），向后兼容 total≥70
- **审计需要验证**：阶段边界压缩是否影响 stage 2/3 训练质量？4:5:1 比例 vs 原 1:1:1.33（30:30:40）是否合理？

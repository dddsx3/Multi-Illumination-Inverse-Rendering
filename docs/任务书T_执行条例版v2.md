## 0. 使用法（先读这一节）

**条例卡字段说明**（每条例固定 8 字段，缺一不可）：
`目标`（一句话）→ `输入`（用到的文件/脚本）→ `步骤`（编号命令，照抄）→ `产物`（路径+命名）→ `证据`（必交的最小文件集合）→ `Git 提交`（提交点 + 信息模板）→ `验收`（数字判据）→ `卡住时`（报错/不达标的固定处置，禁止自由发挥）。

**铁律回顾**：R1 分块夜跑 / R2 冻结复用 / R3 算力账本 / R4 砍臂 / R5 配置冻结（256²·BF16·v3 划分不动）/ R6 证据入库 / R7 散热协议 / R8 人时审计 / R9 单一来源（S 资产只产一次）/ R10 串行 / R11 P 预算硬顶 / R12 叙事卡 / R13 伴生披露 / R14 卸载期 / R15 评审封顶。

**执行者须知**：所有"产物"若与条例不符（路径/字段/数字），等于没做。卡住时按条例"卡住时"分支处理；仍不行 → 停手，把报错原文与现场文件路径贴给主智能体，**禁止自行改代码绕路**。

## 1. 全局操作协议（OP-1 ~ OP-6）

### OP-1 · Git 实时存档协议（解决"怎么实时存档到 GitHub"）

1. **工作目录**：本地仓库 `Multi-Illumination-Inverse-Rendering/`，分支永远 `main`（本项目单分支 + 标签制，不改动）。
2. **提交时机（四个必提交点）**：① 每条例验收通过后立即提交；② 每日晨检完成后提交当日 eval 产物（即使未达验收，也要以 `wip` 提交现场）；③ 每个门禁（G0/G1/…）通过后打标签；④ 任何"卡住待查"现场，先 `wip` 提交再求助。
3. **提交信息模板**（沿用仓库前缀制）：
   `feat(t1): FW 融合权重 v0 通过置换测试 [条例T1-5]` ／ `docs(g0): 资产清点表签署 [条例T0-2]` ／ `fix(t1): 权重归一化分母为零的边界修复 [条例T1-6, INC-0013]` ／ `wip(a3): A3-3 夜跑中断于热墙 epoch72/100 [条例A3-3]`
   前缀只用：`feat`（新功能/新实验落地）、`fix`、`docs`、`wip`（现场保存）、`diag`（诊断）、`audit`（审计）、`freeze`（门禁/冻结）。
4. **推送纪律**：每个提交后立即 `git push origin main`（有网即推）。`git push` 失败（断网/冲突）→ 见 §1.6 处置。
5. **不入库清单**（gitignore 已固化，勿改）：checkpoint、训练日志、`*_SMOKE_*` 产物、运行时状态。**checkpoint 的替代证据** = 每个 run 必须产出 `RUN_CARD.json`（见 OP-2），入库。
6. **checkpoint 物理备份**：每门禁通过日，把 `ckpt/` 新增内容复制到外置盘（U 盘/移动硬盘），复制完成在 `docs/backup_log.md` 追加一行：`日期 | 门禁 | 新增ckpt清单 | 介质 | 校验(文件数+总大小)`。
7. **标签格式**：门禁标签 `gate-<名>-<YYYYMMDD>`，如 `gate-G0-20260913`。推送标签：`git push origin gate-G0-20260913`。
8. **每周日**：跑 `git status` + 看 `docs/backup_log.md`，产出一行周同步记录（沿用仓库 SYNC_VERIFICATION 先例）。

### OP-2 · 证据链协议（解决"证据怎么保存、怎么确认"）

1. **叙事卡文件 `p1/protocol/CLAIM_CARDS.md`**（本阶段新建）：每张共享事实卡一个条目，固定格式：
   `【S-编号】一句话 | 数值 | 来源文件(相对路径+行/表) | 复现命令 | 口径(允许/禁用的措辞) | 登记日期`
   每产出/登记一次 S 资产，10 分钟内追加一行并提交。
2. **RUN_CARD.json**（每个训练/评估 run 必产，与 eval 产物同目录）：
   ```json
   {"run":"A3-3_fw_main","ckpt":"ckpt/fw_main_seed42.pt","ckpt_sha256":"<计算值>",
    "config":{"model":"fusion","modality":"rgb","split_manifest":"splits/synthetic_v3.json",
    "epochs":100,"amp":"bf16","seed":42},
    "eval":{"test":"./eval_output/A3-3_fw_main/eval_summary.json"},
    "produced":"2026-xx-xx","status":"ok|interrupted"}
   ```
   生成命令（Windows 下用 certutil 或 PowerShell Get-FileHash）写入 `docs/run_card_howto.md`，照抄即可。
3. **验收即确认**：任何"数字有效"的确认 = ① 该数字来自入库的 eval json/csv（R6），② 对应叙事卡已登记，③ 门禁裁决书里写了判定行。三者缺一 → 该数字视为无效，不得进入论文。

### OP-3 · 每日节奏（夜跑日 / 纯 CPU 日）

**夜跑日**（有训练任务的日）：
| 时刻 | 动作 | 看什么/做什么 |
|---|---|---|
| 20:30 | 启动前检 | `python run_arms.py --status`；确认无残留任务；散热环境（垫高/充电）；`source _env.sh` |
| 20:35 | 启动 | 按条例卡命令启动 `run_arms.py --budget-hours 6`，记录启动时间到账本 |
| 23:30 | 中途查 | 终端无报错即好；`run_arms.py --status` 看 epoch 进度；异常截图存 `docs/incidents/` 草稿 |
| 次日 8:00 | 晨检 | `run_arms.py --status`；查 loss 曲线最后 20 点无 NaN（看 `eval_output/<RUN>/train_log.csv` 尾部）；热墙停机则确认 resume 点 |
| 8:30 | 产物落地 | 跑条例卡的评估命令；eval json/csv 入库；写 RUN_CARD.json |
| 9:00 | 提交 | OP-1 提交点②：`feat`/`wip` 提交 + push |
| 9:05 | 记账 | 账本追加：`日期 | run | GPU·h(实际) | 结果摘要 | 明日计划` |

**纯 CPU 日**：早 9:00 一个提交点即可（当日产物），其余时间按条例卡做 CPU 任务（A1 设计/A2 定理/A4 归因），每条例验收后提交。

### OP-4 · 算力账本
文件 `docs/gpu_ledger.md`（新建）。表头：`日期|run|预算(h)|实际(h)|状态|备注`。每周日 21:00 加一行周汇总：`本周实际 | 累计 | 距情景预算 +/-`。超支处置见《任务书 v1》§9 裁剪规则（继承）。

### OP-5 · INC（事故）流程
触发条件：任何与预期不符（NaN/发散/热墙中断/数字异常/脚本报错/发现口径问题）。步骤：① 现场保存（`wip` 提交）；② 新建 `docs/incidents/INC-00XX_<短名>.md`，模板沿用仓库现有 INC（时间线/证据链/根因分层/修复/验证五段，照抄 INC-0005 的格式）；③ 修复后跑相关条例的验收判据；④ 在叙事卡或条例中追加"INC-00XX"注记。**禁止不建 INC 就重跑**（INC-0003 教训：冒烟覆盖生产 checkpoint）。

### OP-6 · 命名字典（一切文件名照此，禁止自创）
- 训练 run 名：`<阶段>_<编号>_<短描述>[_seed<X>]`，如 `A3-3_fw_main_seed42`、`A3-1_noFilm`、`A3-2_seed123`。评估输出目录 `eval_output/<run>/`。
- 冒烟 run 名：同名 + `_SMOKE_` 后缀（D12：冒烟产物禁入对比矩阵）。
- 冻结测试命名：`<run>_test`、N 曲线：`<run>_n_curve`（沿用仓库 `p2_t25_f_albOff_n_curve` 先例）。
- 报告文件：`docs/<阶段>_<编号>_<名>.md`。
- checkpoint：`ckpt/<run>.pt`。

## 3. 阶段 A 条例（09-14 → 11-15）

### A1 · FW 融合设计冻结（CPU · 条例 T1-1 ~ T1-6 · 09-14 → 09-28）

#### 条例 T1-1 · 数学形式推导（逐光 Fisher → 权重）
- 目标：写出融合权重的闭式/可微形式，且与 IDENTIFIABILITY_v3 §2–3 的符号完全一致。
- 步骤：① 重读 `p1/protocol/IDENTIFIABILITY_v3.md` §2（F_ll,k、B_k 定义）与 §3（F_eff = F_ss − Σ_k B_k F_ll,k† B_kᵀ）；② 在 `docs/design/T1_fw_fusion_design.md` 中推导：逐光信息量 $I_k$ = 由 F_ll,k 正谱与 B_k 交叉块定义的量（给出明确公式）；权重 $w_k$ = 对 $I_k$ 的归一化单调函数（给出明确公式，注明可微性）；③ 推导"误差-下界理论斜率"：在 homoscedastic 高斯下，albedo 估计的 CRB = $\mathrm{tr}(F_{eff}^{+})/P$ 量级，给出 $E_{min}(N)$ 对 N 的闭式/数值表达式与斜率定义（log-log 或线性，**写清取什么坐标**，否则 G1 无法判）；④ 每一步写清"由哪个定义/公式得到"，公式编号与 IDENTIFIABILITY_v3 对齐。
- 产物：`docs/design/T1_fw_fusion_design.md`（含 §验收判据草案）。
- 证据：设计文档本身（公式链完整可查）。
- Git 提交：`feat(t1): FW 权重与理论斜率推导初稿 [条例T1-1]`
- 验收：独立复核（自己隔天重读一遍或找同组人）：F_ll,k 公式与 v3 §2 逐符号一致；斜率表达式在 N=1 时有意义（不除零）。
- 卡住时：推导不通（例如 trace 伪逆无闭式）→ 不硬推，记录三种替代方案（数值 CRB、代理量、经验拟合），提交后问主智能体选型。

### B1 · 真实数据（条例 B1-1 ~ B1-3）

#### 条例 B1-1 · 拍摄执行（2–3 个拍摄日 + 1 天整理）
- 准备清单（前一晚核对）：暗室（无窗或全遮光）、固定机位（三脚架+标记物定位）、单灯（可移动台灯/手机闪光灯禁用——需方向可控）、灰卡（白平衡）、被摄物 ≥ 3 类材质各 ≥ 6 个（如：哑光塑料/金属/织物，按你手头物品定，写进 `docs/capture_plan.md`）。

  1. 固定相机与被摄物，相机参数锁定（ISO/快门/光圈手动，先拍灰卡定白平衡）；
  2. 灯位序列 ≥ 5 个方向（正面/左/右/顶/45° 组），每灯位拍 1 张，灯与物距固定；

## 2. 三个根因 (按影响排序)

### 根因 1 · D 盘 24GB 页面文件"配置了但没生效" (影响最大)

- 系统里配置了两个页面文件: C: (4-16GB) 和 D: (固定 24GB)
- 但**实际只有 C: 在工作** → Commit 限额只有 27.4GB
- 如果 D: 生效, 限额会变成 **~51GB**, 所有历史故障都不会发生
- 常见原因: 设置后没有重启; 或 D: 页面文件创建失败被静默跳过

### 根因 2 · 物理内存只有 15.2GB, 而 HANDOFF 文档写的是 32GB

- R4PP_HANDOFF §3 写 "RAM 32GB" — **与本机不符** (可能当时写错或指别的机器)
- 这导致此前所有算力估算 (含我在内的) 都按 32GB 规划, 实际可用减半
- 勘误已记入本报告; 历史 handoff 文档按冻结原则不改写

### 根因 3 · 日常负载把 Commit 吃到 86%, 剩余 3.9GB 是"悬崖边"

- 309 个进程, 进程合计 17.9GB commit: WorkBuddy (~1.4GB), 两个 claude
  (~1.3GB), 三个 ZCode (~1.3GB), mysqld (0.6GB), 杀毒 MsMpEng (0.5GB) + 长尾
- 剩余 3.9GB 看似够, 但:
  - torch 加载 CUDA 运行时需要一次性 ~2-4GB commit → 撞墙 → **WinError 1455**
  - CUDA 显存分配在 WDDM 模式下需要系统 commit 做映射 → 撞墙 → **CUDA unknown error**
  - numpy 长跑碎片化 + 突发分配 → 撞墙 → **ArrayMemoryError (2MB 都失败)**
- 凌晨负载下降后同一台机器同一份代码全部跑通 → 证明不是代码/硬件问题

## 4. 修复清单 (你亲自操作, 按 P0 → P2)

### P0 · 让 D 盘页面文件生效 (10 分钟 + 重启, 一劳永逸)

1. `Win + R` → 输入 `sysdm.cpl` → 回车
2. "高级" 标签 → 性能 "设置" → "高级" → 虚拟内存 "更改"
3. **取消勾选** "自动管理所有驱动器的分页文件大小" (如果勾着)
4. 检查两个条目:
   - C: → 选 "自定义大小", 初始 4096 / 最大 16384 (保持现状)
   - D: → 选 "自定义大小", 初始 **24000** / 最大 **24000**
   - 两个都点 "设置", 然后 "确定"
5. **重启电脑**
6. 重启后验证: 任务管理器 → 性能 → 内存 → 右下角"已提交"
   - 修复前: `23.5/27.4 GB`
   - 修复后应为: `xx/51 GB` 左右 (分母变大)
   - 或 PowerShell: `Get-CimInstance Win32_PageFileUsage` 应出现两行 (C: 和 D:)

### P1 · 实验运行纪律 (零成本)

- 跑实验前关掉: WorkBuddy、多余的 claude/ZCode 窗口、不用的 mysqld
- 长实验用"谁也不动"的时段跑 (实验进程自身峰值 ~2-4GB commit, 现在剩余 3.9GB
  是及格线, 修复 P0 后剩余 ~27GB, 随便跑)
- 我已给三个 campaign 脚本加了启动内存体检 (可用 <4GB 会警告)

### P2 · 结构性 (可选, 如果以后要长期本地跑)

- 这台机器的硬上限是物理 15.2GB。P0 修复后 commit 限额 ~51GB, GSIQ/solver
  的需求 (峰值 2-4GB) 绰绰有余, **不需要加内存也能完成 R5 全部实验**
- 如果未来做 P=10000+ 的超大规模实验或同时开多个求解器, 再考虑加内存条
  (THUNDEROBOT RS 需确认是否有空余插槽)
